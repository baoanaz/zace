# zace 多 AI 编排流程（任务分发手册）

> 状态：2026-09-10 编排者制定。所有实施 AI 会话必须遵守；与 `AGENTS.md` 配套使用。
> 一句话：**任务卡是唯一交付合同，文件所有权是唯一的并行边界，契约冻结是唯一的集成保障。**

## 1. 角色

| 角色 | 职责 | 边界 |
|---|---|---|
| 编排者（总览 AI） | 任务拆分与卡片维护、契约冻结与变更裁决、PR 评审、集成复核、设计文档漂移记录 | 不实现业务模块代码；Phase 0 底座与契约文件除外 |
| 实施 AI（子会话） | 认领一张任务卡，在其文件所有权内实现、自测、回填执行记录、开 PR | 不越界改文件；不改契约与设计文档；不顺手做别的卡 |
| 用户 | 分发会话、合并 PR、拍板 L3 决策 | — |

## 2. 任务卡生命周期

```text
pending ──认领──► in_progress ──自测通过+回填──► review ──编排者评审+合并──► done
                     │                                  │
                     └──阻塞──► blocked ◄──评审打回──────┘
```

状态只出现在两个地方，且必须同一次提交内一起更新：卡片文头 `> 状态：` 与 `docs/tasks/README.md` 任务板对应行。

### 泳道模式（本项目默认分发方式）

一个**泳道（lane）= 一个独立工作区（git worktree）+ 一个 AI 会话**，负责一组已按依赖排好序的任务卡（划分见 `docs/plan/dispatch.md`）：

- 泳道内：按卡顺序连续做，一张卡一个分支/提交，**不要等确认**；后续卡从上一张卡的分支创建（同一泳道的代码需串联）。
- 泳道之间：文件所有权互不重叠，可同时开工（同一波次内的卡）。
- 交付：**只需本地分支**（无需 push、无需 PR）；评审、集成测试与合并由编排者执行，合并后用户再开下一波泳道。
- 开新一波前必须已合并上一波（泳道需要主干上的他人代码）。

### 单卡模式（备用，用户手工挑单张卡时）

1. 打开 `docs/tasks/README.md`，挑一张 `pending` 且 **依赖全部为 done** 的卡。
2. 新开实施 AI 会话，首条指令用以下模板：

   > 你负责 zace 仓库的 TASK-002。先读根目录 `AGENTS.md`，再读 `docs/tasks/TASK-002-*.md`，按卡内"输入文档 → 交付物 → 验收标准"执行。完成后按卡内"完成报告"节回填，并更新任务板状态为 review。

3. 一个会话只做一张卡，完成后将分支交编排者评审。

### 认领规则

- 认领时先把卡片状态改为 `in_progress` 并推送（或至少在完成 PR 中说明），避免两个会话抢同一个模块。
- 文件所有权冲突时以任务板状态表为准：同一卡状态为 in_progress 期间，其它卡不得改其交付物清单内的文件（公共文件除外，见 §7）。

## 3. 完成报告模板（泳道模式：本地分支交付）

实施 AI 完成后，在任务卡"执行记录"节与给用户的完成报告中提供：

```markdown
## TASK-002 完成报告
- 分支：feature/task-002_xxx0910
- 验收：`uv run pytest core/tests/parsing -q` → 42 passed；`uv run ruff check .` → clean
- 关键产物：core/zace_core/parsing/base.py、python.py、tests/...
- 契约影响：无 / 见 §4 申请
- 与设计偏差：无 / 说明
- 未决问题：无 / 列表
- 建议复核点：<编排者评审时重点看什么>
```

交付纪律：**不直推 main、不 force push**；泳道模式下只需本地提交（不必 push/PR），评审与合并由编排者执行。

## 4. 契约变更协议（重要）

契约文件清单见 `docs/plan/contracts.md`。任何变更分三级：

| 级别 | 场景 | 流程 |
|---|---|---|
| L1 实现细节 | 不改任何契约文件（`docs/contracts/**`、`zace_core/{types,interfaces,hashing}.py`）的签名/字段/语义 | 直接在卡内实现，PR 说明即可 |
| L2 契约扩展/修改 | 需要新增字段、改签名、改 DDL、改 API 形态 | 在任务卡"执行记录"里写"契约变更申请"（改什么/为什么/影响哪些卡）→ **停止越界实现**，仅提交不依赖该变更的部分；等编排者更新契约文件与受影响卡片后再继续 |
| L3 设计决策变更 | 推翻/修订 INDEX §3 决策（如换向量库、改 RRF 公式） | 编排者提交用户拍板；更新决策登记表 + 对应 Module 文档 + 受影响卡片，再放行实现 |

约束：**实施 AI 永不直接改契约文件与设计文档**。发现契约缺陷时，L2/L3 流程是唯一出路。

## 5. 阻塞与升级

- 卡在实现中遇到无法自决的问题（契约缺失、设计矛盾、参考不可得）：卡片改 `blocked`，在"执行记录"写：阻塞点 / 已尝试的解法与结果 / 需要谁给什么决策。
- `blocked` 卡不占用文件所有权（其它卡可继续）；解除后回到 `pending`。
- 编排者评审发现与设计漂移、契约破坏、验收造假：打回 `in_progress` 并写明原因，不计入完成。

## 6. 里程碑集成检查（M1，编排者执行）

```bash
# 0. 基线全绿
uv run ruff check . && uv run python scripts/check_dependency_direction.py && uv run pytest
# 1. 对 zace 自身仓库做全量索引（dogfooding）
uv run zace-core ingest --repo . --data ~/.zace-test
# 2. 中文/符号混合查询冒烟（人工核对行号与证据分层）
uv run zace-core search "token 过期后在哪里刷新" --repo .
# 3. 增量验证：改一个函数的 docstring，确认只重嵌该 chunk
# 4. golden set 基线报告
uv run zace-core eval --golden benches/golden/ --report benches/results/phase1.md
```

四项全部通过且报告留档 → M1 达成，才允许进入 Phase 2 体验建设。

## 7. 并行规则速查

| 规则 | 说明 |
|---|---|
| 一张卡一个会话 | 不并行做多卡；不顺手重构其它模块 |
| 目录所有权 | 以卡内"交付物"清单为准；公共文件（根 pyproject/CI/README/任务板）改动前先在卡内申请 |
| 基线绿 | 每次提交前跑 §6-0 的三条命令；破坏基线不得声明完成 |
| 文档漂移 | 代码与设计不一致但已合并的：编排者在 Module 文档修订记录登记，实施 AI 不自行改文档 |
| 参考源码只读 | `../source/` 只读；禁止 copy-paste 参考项目实现（Demo.md §1：学习架构不复制实现） |
