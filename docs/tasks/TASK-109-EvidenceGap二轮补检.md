## 为什么需要它（由真实失败驱动，不是设计推演）

2026-09-15 用 cockpit-agents-py 做 6 次真实调用（3 search + 3 ask）逐项对照本地源码，暴露出
**同一类系统性缺陷**：候选已正确索引，但**没被召回**，导致包内缺关键实现。

| 题 | 现象 | 根因 |
|---|---|---|
| S1 | 漏 `runtime.py:43`、`dispatcher.py:213` 与后续执行链 | 需要跨文件调用链，当前只有词法+语义 |
| S2 | `_commit()` 与 Coordinator 调用位置不全 | 同上 |
| S3 | 查 Gateway 幂等/验证/重试，包内**无 `capability/gateway.py`** | 目标函数 rank 72（`_reserve_idempotency`）、`_should_retry`/`_normalize`/`_verify` **连候选池都没进** |

**关键证据（S3）**：`gateway.py` 的 37 个 chunk **全部正确索引**（`_reserve_idempotency` 在
336-352 行、`_should_retry` 在 486-503 行），但首轮召回一条都没进来。这不是索引缺失、
不是排序错误、不是预算截断——是**召回覆盖不足**。

同一批测试里也确认了一个**反例**：TASK-108 的测试夹具常态抑制修好了「测试挤占实现」
（S3 包内测试从 20 条降到 1 条、token 从 9912 降到 4698），但**`gateway.py` 仍未进包**
（因为它的候选本身排在 rank 72）。这恰好证明**噪音抑制与召回补检是两件不同的事**，
后者必须靠本卡。

## 设计要点（讨论基线，实施前需评审）

### 1. 只做 G1/G2/G3（G4/G5 已有归属）

| 规则 | 本卡处理 |
|---|---|
| **G1** 调用链断裂 | ✅ 核心：2-hop 定向图查询，只从 top 种子出发，不全量重跑 |
| **G2** 设计意图缺失 | ✅ spec evidence=0 时用首轮代码符号反查 `spec_references` |
| **G3** 无共识结果 | ✅ top10 全单通道时，用 top3 的符号名/文件名构造扩展查询 |
| G4 文档过时 | ❌ TASK-096 已实现（进 MissingEvidence，不触发二轮） |
| G5 预算富余 | ❌ 属组装层（TASK-108 已把闸门改为优先级语义） |

### 2. 二轮纪律（设计已定，不得放宽）

- 最多 **1 次**迭代；
- 二轮只补缺口对应的通道（G1 只走图、G3 只重召回），不做全量重跑；
- 二轮结果**进同一 rerank**，不直接插队（否则破坏 D-16 的排序唯一性）；
- 全部 deterministic，不引入 LLM（R1 的延迟预算）。

### 3. 与现有预算/闸门的关系

二轮候选进池后，仍走同一套 `score_floor` 与预算装填。**不因为"是二轮来的"就绕过闸门**——
否则会重演 TASK-108 之前的"把 0 分/负分候选塞满预算"。

### 4. search 与 ask 都要有

- `search_context`：Fast 模式也触发（成本是本地查询，非 LLM）；
- `ask_project`：Deep 模式触发，效果叠加。

两者的分叉点必须在**组装之后**（D-10）：同一份 `gap` 结果喂给同一个 assemble。
