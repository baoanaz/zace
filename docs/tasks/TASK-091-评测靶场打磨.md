> 明天我仔细打磨两个工具的返回内容，以及补全多个真实的问题，打磨 benchmark 的设计。

本卡就是把标尺做好，为 TASK-050（质量调优）铺路。

## 目标

交付一套**可信、可复现、能反映真实使用分布**的评测靶场与 golden 集。

## §A 用例设计（核心工作）

**用户要求"补全多个真实的问题"** —— 请按以下维度扩充用例：

| 维度 | 要求 |
|---|---|
| **真实来源** | 优先来自**真实使用日志**（`query_audit` 表已有真实查询，TASK-084 的副产物）或你/用户真实会问的问题；**不要凭空编造** |
| **分布覆盖** | 中/英/中英混合三种语言；符号类/语义类/跨文件调用链类/设计意图类/负例 五类 |
| **难度分层** | 简单（单个符号定位）/ 中等（跨 2-3 文件）/ 难（调用链、Spec vs 实现一致性） |
| **负例** | 必须包含"仓库里确实没有"的问题（验证 `answerable=false` 不幻觉）；**负例要与正例同分布**，不能一眼看出是负例 |
| **规模** | 建议扩到 **60-100 条**（当前 31 条），且**每条都要 grep 核验 expected 真实存在** |

**出题纪律（沿用 TASK-014，不可放松）**：

- 每条 `expected` 必须 **grep 核验过**（把核验命令写进 `notes`）；
- 负例必须**真的 0 命中**；
- **不得为了数字好看而挑易用例子集**（R29/R30）；
- `commit` 字段要钉住（靶场是外部仓库，会变）。

## §B 指标设计（如需扩展）

现有指标：`recall@5` / `recall@10` / `MRR` / 负例通过率。

**用户要"打磨 benchmark 的设计"**，请评估是否需要新增（**你判断，报告说明理由**）：

| 候选指标 | 衡量什么 | 是否需要 |
|---|---|---|
| `citationCoverage` | 引用回验的覆盖率（TASK-088 已有该数据） | 建议：LLM 接入后才有意义 |
| 首次命中层级（tier/rank 分布） | 正确答案排在第几位 | 建议：比 recall 更有诊断价值 |
| `next_queries` 有效率 | 建议的改问是否真的能召回到目标 | 建议：TASK-087 后才有 |
| 端到端延迟（P50/P95） | 是否满足 `ask_project <10s`（文档 L2） | 建议 |
| token 预算利用率 | 装填是否浪费预算 | 可选 |

**新增指标要求**：必须在 `benches/README.md` 写清定义与计算口径，且**能被现有 runner 复现**。
