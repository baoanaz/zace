# 索引性能基准：冷启动 / 增量 / 瓶颈归因（2026-09-13）

> 编制：编排者（本机实测，全部数字可追溯）。
> 被测对象：合并 W6 三泳道后的 `main`（`01d9016`）。
> 靶场：`/home/xuwenzheng/github/hello-agents` @ `4f7682c`（1436 索引文件 / 9389 chunks）。
> embedding：硅基流动 `BAAI/bge-m3`（免费档，1024D）。
> 机器：WSL2 / 12 逻辑核 / 15 GiB（**单线程嵌入，未并发**）。

## 1. 一句话结论

| 问题 | 答案 |
|---|---|
| 冷启动多久？ | **约 3.8 分钟**（230s；此前 1482 文件时为 284s） |
| 增量多久？ | **改 1 个文件 = 4.1 秒**（其中 2.6s 是进程启动 + 增量对账 + 重建图边） |
| 无改动重跑？ | **1.8 秒**（纯对账） |
| 瓶颈是什么？ | **云端 API 的 TPM 配额与往返次数**（嵌入占冷启动 99.3%）；**不是**模型算力、也**不是**本地 CPU |
| 付费能改善吗？ | **能，且比预期更关键**：免费档的真实天花板是 TPM 限流；调批参数实测仅 **1.31×**（非理论 4×），付费买的是**配额**。日常增量场景免费档完全够用 |

## 2. 冷启动耗时拆解（9389 chunks / 384 万 token）

```text
总墙钟 230.9s
├─ 解析 + 切分（本地纯 CPU）      1.5s   (0.7%)   ← 941 文件（markdown 227 / python 714）
├─ 嵌入（云端 API）            ≈229s   (99.3%)  ← 唯一的成本项
└─ 入库 + 建图 + 向量写入        ≈0.4s   (0.2%)
```

**本地计算不是瓶颈**：整个仓库的树解析 + 切分只要 1.5 秒。全部时间都花在等 API。

## 3. 增量索引（日常改代码）

| 场景 | 墙钟 | 核心耗时（`elapsed`） | 实际重嵌 |
|---|---|---|---|
| 无改动重跑（稳态对账） | 1.84s | 0.7s | 0 个 |
| 改 1 个文件（追加 1 个函数） | **4.08s** | 2.8s | **2 chunks**（其余 7 个按 content hash 复用） |
| 还原该文件 | ~4s | 2.6s | 1 chunk（复用 7） |

**结论**：内容哈希复用机制工作正常——改一个函数只重嵌受影响的 chunk，不重建整个文件。
**4 秒的构成**：进程启动 ≈1.3s + 增量扫描对账 + 2 次 API 往返（约 0.5s）+ 建图边重定向。
**日常改代码的感知延迟是秒级，不是分钟级。**

## 4. 瓶颈归因（关键）

### 4.1 不是模型算力，是往返次数

实测同一批输入、不同批大小的吞吐：

| 批大小 | 输入 token | 耗时 | 吞吐 | 单条摊销 |
|---|---|---|---|---|
| 1 条 | ~100 | 1.51s | — | **1510 ms/条** ← 几乎全是网络往返 |
| 8 条 | ~800 | 0.21s | — | 26 ms/条 |
| 40 条 | ~5.6K | 0.29s | 11 K tok/s | 7.2 ms/条 |
| 64 条（真实 chunk） | 21.1K | 0.81s | 26.2 K tok/s | 12.6 ms/条 |
| 256 条（真实 chunk） | 55.1K | 1.53s | **36.0 K tok/s** | 6.0 ms/条 |
| 512 条（真实 chunk） | 89.9K | 2.11s | **42.6 K tok/s** | 4.1 ms/条 |
| 700 条（真实 chunk） | 89.9K | 2.16s | 41.6 K tok/s | 3.1 ms/条 |

**读法**：
- 单次请求的空载往返约 **95–105 ms**（TCP + TLS + 网关 + 排队）；
- 同样 9000 条文本，按 64 条/批需要 **约 141 次往返**，按 512 条/批只需 **约 18 次**；
- 当前 `DEFAULT_BATCH_TOKEN_BUDGET = 8192` 让批被 token 预算卡得很小（真实 chunk p50=169 token →
  每批只装约 48 条）→ **往返次数被放大 8–10 倍**。

### 4.2 云端的硬上限（实测边界）

| 探测 | 结果 |
|---|---|
| 极短文本 × 760 | HTTP 200（2280 token） |
| 极短文本 × 800 | **HTTP 500** |
| 真实 chunk × 760 | HTTP 200（约 96K token） |
| 单条 9000 token | HTTP 400（超 8192 上限，已被 TASK-046 的截断修复覆盖） |

→ 硅基流动 embedding 接口有**约 800 条的条数硬上限**（与 token 总量无关）；
当前 `batch_size=64` 离它很远，仍有 **10 倍以上**的提升空间。

### 4.3 429 限流情况（补充）

- 免费档存在 **TPM 限流**，实测可持续约 **200K token/min** 时较稳定；
- 冷启动总需求 384 万 token，按 200K/min 约需 **19 分钟**——但实测 230s 跑完，
  说明**稳定批处理（无尖峰）下不会被限流**；429 主要出现在**多泳道共用同一 key 争抢**时；
- TASK-046 已实现：429 指数退避 + `Retry-After`（上限 30s）+ 最多 2 次重试后抛出（不无限重试）。

## 5. 建议（按性价比排序）

| # | 措施 | 预期收益 | 成本 | 备注 |
|---|---|---|---|---|
| **1** | **提高批预算**：`DEFAULT_BATCH_TOKEN_BUDGET` 8192 → **24000**，`batch_size` 64 → **128** | 实测嵌入阶段 **93.6 → 122.8 chunk/s（1.31×）**；冷启动 230s → **约 175s** | 免费（改常量 + **加环境变量入口**） | **有限提升，非 4×**（见 §4.4 的订正）；**TPM 限流仍是天花板**，故不可冒进放大 |
| **2** | **并发请求**：2–3 路并行批 | 理论可再提升，但**会更快撞 TPM**（实测跑到约 200 K tok/min 即 429） | 免费 | 需先摸清配额上限；建议与 #1 一起做并**实测限流边界** |
| **3** | **付费档** | **提升配额上限**（直接抬高 TPM 天花板，这才是当前真正的限制） | ¥0.07/M token 档 | 按本靶场 384 万 token/次全量：**约 ¥0.27/次**；日常增量微不足道。**若经常撞 429，付费是性价比最高的一步** |
| **4** | 本地 ONNX 兜底 | 不受网络/配额影响 | 已暂缓（U1/U2） | 未来隐私/脱网场景 |

**回答"付费能不能改善"**：**能，而且比原先估计的更关键**。

- **免费档的真实天花板是 TPM 配额**（不是每次请求的批大小）：实测单请求能一次吃下 72 K token（760 条），
  但**持续高速请求会被限流**；
- 因此"把批调大"的收益**有上限**（实测 1.31×，而非理论推算的 4×）——因为批一大就更快撞限额；
- **付费买的是配额，不是速度**：若你频繁跑全量索引/多仓库，付费档能直接抬高天花板，
  且按用量估算**月成本远低于 10 元预算**；
- 若只在**日常增量**场景（改几个文件 = 几秒钟），**免费档完全够用**，无需付费。

### 4.4 一个被订正过的判断（诚实记录）

编排者最初由"批越大越快"的探测数据外推出"批预算调到 65536 可把冷启动降到 55–60s（4×）"，
**该推算被实测推翻**：

1. 先用 `EMBED_BATCH_TOKEN_BUDGET=65536 EMBED_BATCH_SIZE=256` 跑全量索引 → 耗时 **231s，与默认无差别**
   （根因：`factory.from_env` **根本没有读这两个环境变量**，TASK-046 只加了构造参数、未加配置入口）；
2. 改为在进程内直接传参重测（9389 真实 chunk）：
   - 默认（budget=8192 / bs=64）→ **441s**（比全量索引慢，因为未复用可能被 429 拖累）；
   - 提到 budget=65536 / bs=256 → **直接 429 失败**；
3. 退到固定 2000 条样本、只改批大小的干净对比：**93.6 → 122.8 chunk/s（1.31×）**。

**结论**：收益真实但有限（约 1.3×），**TPM 限流是真正的天花板**——这正是付费档最大的价值。
报告初稿中"4×"的说法已在此订正（保留过程以示诚实）。
