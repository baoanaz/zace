# 三仓库 60 题审计与 core 架构建议（2026-09-15）

> 状态：题库已修订，core 未改动｜设备：`vps-la-2c2g`｜任务：TASK-091
> 索引：`/root/.zace/bench/voyage-4-lite-d1024`（全程复用，未 ingest）
> 固定版本：leveldb `7ee830d`、HelloAgents `93e77ea`、langchain `41d3572`

## 1. 结论

这 60 题适合作为**首批跨规模、跨语言仓库的确定性回归集**，但修订前不能直接当作可信的
端到端答案正确率基准：题目全部是中文，10 条参考答案存在事实错误或明显误导，若干跨文件题只要
命中任意一个 expected 就算成功，`answer_hit` 又只检查答案有没有写出文件路径。

本轮完成三类 benchmark 修订：

1. 修正源码事实与证据范围；
2. 在不改变知识点数量的前提下，把语言分布从 `zh=60` 改为
   `zh=33 / en=12 / mixed=15`；
3. 为跨文件 ask 增加 `expected_mode=all`、逐项证据覆盖率、完整命中与期望证据引用指标，
   同时保留 v1 `answer_hit` 字段作兼容，但不再把它解释为答案正确率；评测器也改为在
   `answerable=false` 时按 D-24 短路，不再绕过生产分支调用 LLM。

core 本轮没有改。最高优先级不是盲目增加检索次数，而是修复 C/C++ 解析失败时整文件降级导致的
结构信息丢失；完成后必须重建 leveldb 索引，再用本题库做前后对照。

## 2. 核验范围与方法

- 三个 checkout 的 HEAD 均与题库 `commit` 完整一致，工作区干净；
- 60 条 JSONL 均可解析，所有 `expected[].path` 存在；
- 所有带 `symbol` 的 expected，其末级符号名都能在对应固定版本文件中找到；
- 对 60 条参考答案逐条读固定版本源码，重点复核常量、默认值、状态机、继承关系、抽象方法、
  跨文件调用与负例；
- 使用当前 `/etc/zace/zace.env` 的 Voyage query embedding 和 AnswerProvider 完整重跑一次；
- 对失败题额外记录 recall→rerank 候选路径排名、ContextPack 排名、通道组成，并直接查询
  `index.db` 的 symbols/chunks/files 表确认索引事实。

## 3. 修订前实测

| 仓库 | search R@5 | R@10 | MRR | 负例 | ask pack hit | 路径点名 |
|---|---:|---:|---:|---:|---:|---:|
| leveldb | 0.7143 | 0.7143 | 0.3869 | 1/1 | 1/5 | 2/5 |
| HelloAgents | 0.7692 | 0.9231 | 0.6926 | 0/1 | 5/6 | 1/6 |
| langchain | 0.6429 | 0.6429 | 0.6429 | 0/1 | 5/5 | 1/5 |

修订前脚本让 16 条 ask 全部得到 LLM 输出；AnswerProvider 延迟 P50 `6888.3 ms`、P95 `13889.8 ms`，
平均 `7572.7 ms`。citation coverage P50 `0.8333`，均值 `0.7845`。

“路径点名”在历史 v1 是 8/16，本轮只有 4/16，但逐题阅读可见很多答案只写 `[E*]` 而不重复
路径。这是旧 `answer_hit` 指标失真，不是 LLM 正确率从 50% 跌到 25%。

此外，旧脚本直接调用 `answer_question()`，没有复现 service router 的 D-24 分支；因此
`pack.answerable=false` 也被记为 answered。v2 已修正为短路并记录 `short_circuited`。

## 4. 题目与答案修订

### 4.1 事实错误或明显误导（已修）

| ID | 原问题 | 源码事实与修改理由 |
|---|---|---|
| L-04 | Footer 固定 40 字节 | `Footer::kEncodedLength = 2 * 20 + 8 = 48`；40 只是两个 BlockHandle 加 padding，后面还有 8 字节 magic。增加 `table/format.h#Footer` 证据。 |
| L-16 | memtable 一定变成 level-0 sstable | `WriteLevel0Table` 会调用 `PickLevelForMemTableOutput`，满足无重叠条件时可直接放 level 1/2。问题与答案改为询问完整落盘和选层流程，并补齐四个 expected。 |
| L-18 | 大于“剩余空间四分之一”时单独分配 | 判断是 `bytes > kBlockSize / 4`，即大于固定 4KB block 的四分之一，不是当前剩余空间的四分之一。 |
| H-03 | `auto_expand` 展开参数 schema | 实际是 expandable 工具通过 `get_expanded_tools()` 展成多个独立工具；与参数 schema 无关。 |
| H-05 | 把目标协议行为当成已接线实现 | `ObservationTruncator.truncate()` 返回 dict 并保存全文，但自身不返回 `ToolResponse.partial()`；答案改为区分协议应然行为与当前实然行为。 |
| H-16 | TraceLogger 只写 JSONL | 实际同时写 JSONL 和 HTML；JSONL 实时 flush，HTML 增量写入并在 finalize 时补统计。 |
| LC-07 | VectorStore 必须实现 add_texts + similarity_search | 当前 commit 的抽象方法是 `similarity_search` 与 classmethod `from_texts`；写入时 `add_texts`/`add_documents` 至少覆盖一个即可，基类会互相适配。 |
| LC-09 | InMemoryCache 是默认缓存 | 它是内存实现，但不会自动启用；需通过 `set_llm_cache` 等配置。 |
| LC-14 | hash + timestamp 决定 skip/update | 内容与 metadata 的 hash id 是否已存在、以及 `force_update` 决定 skip/update；timestamp 用于刷新和 cleanup 识别旧记录。 |
| LC-18 | 纯字符串可表示 system/human | 纯字符串只等价于 human message；补全五类 message representation，并区分 `{var}` 与 MessagesPlaceholder/`("placeholder", ...)`。 |

### 4.2 证据或判分范围不完整（已修）

- H-12：真正触发一致性检查的是 `BaseAgent.load_session`，SessionStore 只提供两个检查方法；
  expected 补入 agent.py 和两个检查方法，且设为 `all`。
- LC-01：问题只问“在哪个文件”，原 expected 却要求类定义符号；top-1 已是同文件的 `parse`

- L-16、H-05、H-10、H-12、LC-10、LC-16、LC-18：这些答案需要多个证据点，增加
  `expected_mode=all`。core eval 仍可报告 any-hit recall，qa_probe 额外报告完整覆盖。

### 4.3 分布问题（已修）

修订前 60 条 `lang` 全是 `zh`，无法判断英文和中英混合查询。每仓保留 11 条中文，将不改变
知识点的 4 条改为英文、5 条改为中英混合。这样既保留中文主体，也覆盖代码检索最常见的
“中文意图 + 英文标识符”形态。

当前仍有两个残余限制：每仓只有 1 条负例，总负例率 5%；所有问题仍是人工设计而非真实用户
日志采样。后续应由 TASK-093 补真实查询分布，不能为提高当前 60 题分数而挑题。

## 5. 失败根因

### P0：C/C++ 单点语法错误导致整文件结构索引清零

`db/db_impl.cc` 只有三处 tree-sitter ERROR（L1063-1065），但现行基座规则是只要出现任意
ERROR/MISSING，就令整个文件 `fallback=True`。数据库中该文件因此只有两个 fallback chunk：

```text
db/db_impl.cc:(module):1    lines 1-788
db/db_impl.cc:(module):789  lines 789-1579
```

`DBImpl::Get`、`DBImpl::Write`、`DBImpl::CompactMemTable` 等符号均不在 symbols 表。L-14 即便
显式写出 `DBImpl::Get`，Exact 通道仍为空。这同时解释 L-09/L-10/L-14/L-16 的 ask 证据缺失。

这不是 rerank 权重问题，也不能靠重复同一 query 解决：索引里没有结构化目标可召回。

### P1：候选已召回，但路由/排序/装填不能区分用户要的证据形态

| ID | 目标路径候选排名 | 包内情况 | 现象 |
|---|---:|---|---|
| L-03 | 12 | 未装填 | `compaction` 让 version_set.h 的类/方法占据前列，常量定义落后。 |
| L-05 | 27 | 未装填 | db/log_format.h 与 doc/impl.md 压过专门的 doc/log_format.md。 |
| L-11 | 9 | E11 | 目标已接近 top-10，但装填后超过评测 top-10。 |
| L-12 | 23 | 未装填 | VersionEdit 头文件声明和 MANIFEST 文档压过 EncodeTo 实现。 |
| LC-06 | 48 | 未装填 | 大仓中大量测试的 `my_tool` 压过 `@tool` 定义。 |
| LC-08 | 30 | 未装填 | 架构文档与 namespace mapping 压过 InMemoryVectorStore。 |
| LC-19 | 36 | 未装填 | `rank_fusion` 近义结果压过明确依赖 `rank_bm25` 的文件。 |

当前 Engine 实际始终走 General/Fast：设计中的轻路由四分支和 Deep Evidence-Gap 二轮没有落地。
因此“问文档格式”“找定义还是实现”“跨文件机制”都使用相同配额与同一轮召回。

### P1：answerable 把双弱通道共识误当可回答

HelloAgents H-20 和 langchain LC-20 都是确认过的负例，但 BM25 与 Vector 同时命中“名字沾边”
的 README、SQLiteEntityStore 等候选后，系统判 `answerable=True`。当前规则奖励通道共识，却不要求
查询关键限定词在证据中被覆盖；已有 `query_partially_matched` 只追加 missing evidence，不会反转
answerable。这会让 ask 对仓库不存在的能力仍调用 LLM。

### P2：评估器把“任一证据命中”当成跨文件答案完整

旧 `pack_rank` 对 expected 使用 OR。LC-16 需要三个 Runnable 文件，命中一个就算成功；H-12
需要调用者和两个检查方法，命中 SessionStore 类也可能算成功。v2 的 `pack_expected_coverage` 与
`pack_complete` 用于揭示这一差异。

## 6. core 修复建议

### 6.1 P0：局部解析容错，不要按整文件二元降级

建议单独开解析任务卡，目标不是简单把“允许 ERROR 数”从 0 调大，而是：

1. tree-sitter 根节点有错误时，跳过 ERROR 覆盖的最小子树，继续抽取不与错误区间相交的
   namespace/class/function 子树；
2. 对成功抽出的 symbol/chunk 保留 `parse_errors` 与可信度来源，错误区间另产 fallback chunk；
3. 只有根节点严重破坏、抽取器异常或正常子树覆盖率低于下限时才整文件 fallback；
4. 增加 leveldb `db_impl.cc`、宏密集头文件、局部损坏函数的真实回归样本；
5. parser fingerprint 变化后换数据根或全量重建三个索引，不能拿旧索引测新 parser。

验收至少应包含：`DBImpl::Get/Write/CompactMemTable` 进入 symbols 表；错误区间仍如实报告；
现有 C/C++ parser 单测全绿；leveldb ask 的目标证据覆盖明显改善。

### 6.2 P1：实现 Evidence-Gap 驱动的第二轮，不做固定 N 次盲搜

用户提出“单次检索很短，可以多检索”方向是对的，但应按缺口定向触发：

- G1：首轮命中 callee（MemTable::Get、Version::Get）却缺调用者时，做反向 callers/2-hop 图补检；
- G2：问题询问格式/设计而 doc=0 时，提高 SpecBlock 定向召回；
- G3：top-10 全是单通道或只命中同主题声明时，用 top symbol/path 构造一次扩展查询；
- G5：预算仍富余但相关候选被相对阈值裁掉时，只重组装，不再调 embedding。

最多一轮，所有新增候选回到同一 rerank，不直接插队。这样额外成本通常是一轮本地查询或一次
query embedding，远低于 LLM 的 6-14 秒，并且结果可解释、可设预算。

### 6.3 P1：让路由表达“定义/实现/文档/流程”需求

无需引入 LLM planner，可在既定四分支内补确定性信号：

- query 含 `在哪个文件/defined/implemented/@symbol`：Symbol/Path，Exact 与 path/symbol 名强召回；
- query 含 `格式/协议/文档/限制`：Docs，提高 spec 配额；
- query 含 `流程/顺序/为什么/调用`：Structural，优先函数体、caller/callee 与 flow；
- “序列化入口/实现在哪”对 `.cc/.py` 定义加分，对 `.h` 声明和测试夹具降权。

先报告各路由分桶指标，再校准权重；不要直接针对 60 个 query 写关键词特判。

### 6.4 P1：answerable 需要相关性闸门

建议将“BM25 + Vector 双弱通道共识”从充分条件改为必要但不充分条件，再叠加至少一项：

- query 内容词/限定词覆盖达到下限；
- 强 literal/exact 命中；
- top 候选的绝对或相对分数通过按仓库规模标定的阈值；
- Deep 补检后仍有两个相互独立的目标证据。

负例至少扩到每仓 4-5 条，并覆盖“存在相邻概念但目标能力不存在”，否则阈值很容易过拟合。

### 6.5 P2：区分索引层、候选层、装填层和回答层指标

建议固定输出四层：

1. index health：解析失败文件数、fallback 文件/行占比、symbols per KLOC；
2. candidate recall：目标在 rerank 后候选池的 rank；
3. pack coverage：目标是否进入包、多 expected 的覆盖率与完整性；
4. answer quality：期望证据引用、citation coverage、人工 rubric 正确/部分/拒答/错误。

只有第 4 层能叫答案正确率。`answer_path_mentioned` 可以保留作可读性诊断，不能作为质量主指标。

## 7. 推荐实施顺序

1. P0 局部解析容错；重建 leveldb 索引并复跑 v2。
2. 接通现有设计中的轻路由与 Deep Evidence-Gap 二轮；先不调全局 rerank 权重。
3. 收紧 answerable，并用扩充后的困难负例验证 false positive/false negative。
4. TASK-093 接真实用户查询后再解冻权重、docs ratio 与装填相对阈值。

不建议当前就做：固定重复检索 2-3 次、为单题加硬编码同义词、单纯扩大 ContextPack、直接换
AnswerProvider 模型。这些措施要么重复得到同一候选，要么掩盖索引缺失，要么增加成本但不增加证据。
